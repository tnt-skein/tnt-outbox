# Ящик исходящих

`tnt-outbox` — ящик исходящих (outbox) для Tarantool. Событие пишется
строкой спейса **в той же транзакции, что и данные**, а уходит отдельным
вывозом: откат уносит обоих, фиксация оставляет обоих, и «сохранили
и отправили» перестаёт терять события при обрыве между двумя действиями.

```lua
local outbox = require('tnt.outbox')

outbox.configure({ senders = { ['order.paid'] = webhook } })   -- кому отправлять
outbox.start()                                                 -- ящик заведён, вывоз пошёл

box.atomic(function()
    orders:insert({ 11, 'оплачен' })
    outbox.write('order.paid', { order = 11 })                 -- событие — строкой той же транзакции
end)
```

Отправитель приходит аргументом: это любая таблица с
`send(name, body, opts)`, и ящику всё равно, брокер за ней, вебхук или
очередь другого кластера. Гарантия — хотя бы раз: повтор несёт тот же
опознаватель, и отсекает его получатель — отметкой второго модуля
пакета, `tnt.outbox.inbox` (раздел «Отметки получателя»).

Зависимости: `tnt-message` (проверка настроек записи и тела, заголовки
контекста в строке — общая часть договора очереди), `tnt-must` (проверки
аргументов), `tnt-clock` (время записи, отметки и планировщика), `tnt-id`
(опознаватель ULID), `tnt-log` (журнал), `tnt-loop` (такты вывоза
и уборки отметок), `tnt-retry` (отступ после отказа), `tnt-metrics`
(ряды ящика) и `tnt-external` (подмена транзакции, спейсов и часов
в проверках). Остальное — `box`
Tarantool.

## Зачем пакет

«Сохранили и отправили» двумя действиями теряет событие при обрыве между
ними, и потеря тихая: данные есть, события нет, и узнать об этом неоткуда.
Отправить прямо в транзакции тоже нельзя: отправитель ходит по сети,
уступка рвёт транзакцию, а ушедшее сообщение откат не вернёт. Ящик делает
два действия одним.

| | «сохранили и отправили» | `tnt-outbox` |
|---|---|---|
| данные и событие | две записи, между ними обрыв | одна транзакция |
| откат данных | событие уже ушло | события нет |
| брокер лежит | вызывающий ждёт либо теряет | строка лежит в ящике, вывоз повторяет |
| порядок | какой вышел | по ключу спейса, строго |
| гарантия | никакой | хотя бы раз |

Пакет делает для этого шесть вещей:

- **Запись — вставка в транзакции вызывающего.** `outbox.write` кладёт
  строку в спейс `outbox`, и откат уносит её вместе с данными. Вне
  транзакции запись идёт своей транзакцией на одну строку и служит
  надёжной отправкой, которая переживает перезапуск.
- **Отправляется только зафиксированное.** Без MVCC строку транзакции,
  ждущей записи в WAL или кворума, видят все, и вывоз, судящий
  по видимости, отправил бы событие, которого после отката не было.
  Вывоз берёт строку, только если знает о её фиксации.
- **Порядок держится ключом.** Ключ строки — последовательность спейса,
  вывоз идёт с начала ящика, и строка, на которой отправитель отказал,
  ждёт, а не пропускается.
- **Отказы разделены.** Повторяемый оставляет строку на месте
  и откладывает вывоз растущим отступом; неповторяемый уводит её
  в `outbox_dead`, и вывоз идёт дальше. Когда отправителя починят,
  `outbox.kick` возвращает зарытое на отправку.
- **Опознаватель и заголовки ставит запись.** ULID и заголовки контекста
  ложатся в строку в миг `write`, и повторная отправка несёт те же.
- **Настройки проверяются при записи**, а не на вывозе через час:
  незнакомый ключ, настройка, которой отправитель не умеет, тело не из
  простых данных — исключение на строке вызывающего.

Ящик нужен для отправки **наружу**: брокер, вебхук, очередь другого
кластера. Очереди в спейсе того же узла он не нужен — её запись и так
часть транзакции.

Вторая сторона той же гарантии — получатель. Повтор приходит к нему
с тем же `id` от любой долговечной очереди, и отсекает его отметка
`tnt.outbox.inbox` в транзакции обработчика: запись и отметка
фиксируются и откатываются вместе, а старые отметки стирает уборка
по сроку.

## Как пользоваться

### Отправитель

Отправитель — таблица с функцией `send` и, если нужно, таблицей признаков
`features`:

```
send(name, body, opts) → id | nil, err
```

`name` — имя назначения, `body` — тело, `opts` — настройки, сохранённые
записью: `id`, `headers` и то, что назвал пишущий (`key`, `delay`, `ttl`,
`priority`, `timeout`). Удача — любое значение, кроме `nil`, обычно
`opts.id`. Отказ — `nil, err`: `err.retriable == false` говорит, что
повтор бесполезен, а всё прочее — `err` без этого поля, `nil, nil`,
брошенная ошибка — считается повторяемым. Текст причины вывоз берёт
из `err.message`, если он есть, иначе из `tostring(err)`; у `nil, nil`
причина — «отправитель отказал и причины не назвал».

`features` говорит, что отправитель умеет из `key`, `delay`, `ttl`
и `priority`: `false` у признака значит «не умею», и запись с такой
настройкой отвергается сразу. Нет таблицы или нет признака — умеет.
`headers`, `id` и `timeout` умеют все.

Вебхук поверх встроенного `http.client`:

```lua
local http = require('http.client')
local json = require('json')

local webhook = {
    send = function(name, body, opts)
        local reply = http.post('https://hooks.example.org/' .. name, json.encode(body), {
            headers = {
                ['content-type'] = 'application/json',
                ['idempotency-key'] = opts.id,                 -- по нему получатель отсекает повтор
                ['x-request-id'] = opts.headers['x-request-id'],
            },
            timeout = opts.timeout or 5,
        })

        if reply.status >= 200 and reply.status < 300 then
            return opts.id
        end

        return nil, {
            message = ('вебхук %s ответил %d'):format(name, reply.status),
            -- 4xx, кроме 429, повтором не лечится: строку — в зарытые
            retriable = reply.status >= 500 or reply.status == 429,
        }
    end,
    features = { key = false, delay = false, ttl = false, priority = false },
}
```

Обрыв сети `http.client` отдаёт статусом 595, и он повторяемый.

### Настройки: `configure`

```lua
outbox.configure({
    senders = { ['order.paid'] = webhook, ['order.shipped'] = webhook },
    interval = 1,
    batch = 100,
    backoff = { base = 1, factor = 2, jitter = 0.5, max = 60 },
})
```

| Ключ | Что | Умолчание |
|---|---|---|
| `senders` | отправители по именам назначений | нет, и запись без отправителя — исключение |
| `interval` | как часто идёт вывоз, секунды; больше нуля | 1 |
| `batch` | сколько строк вывозится за проход; целое больше нуля | 100 |
| `backoff` | отступ после повторяемого отказа по `tnt-retry`: `base · factor^(отказов−1)`, не больше `max`, с разбросом `jitter` | `{ base = 1, factor = 2, jitter = 0.5, max = 60 }` |

Отправители заменяются целиком, а не дополняются: перечитывание
конфигурации обязано уметь снять отправителя. Имя назначения — латинская
буква, дальше буквы, цифры, подчёркивание, точка и дефис: `order.paid`,
`billing.invoice-sent`.

`backoff.factor` — от 1 до 100: меньше единицы пауза сокращалась бы
с каждым отказом. `backoff.jitter` — только доля от 0 до 1: стратегия,
которая считает паузу от прошлой, вывозу не годится — прошлую паузу
между тактами никто не держит. `base` и `max` — не меньше нуля.

Негодная настройка — исключение на строке вызывающего:

```lua
outbox.configure({ interval = 0 })
--> error: настройки ящика.interval — число больше 0, а не 0

outbox.configure({ backoff = { factor = 0.5 } })
--> error: настройки ящика.backoff.factor — число от 1 до 100, а не 0.5

outbox.configure({ senders = { orders = { features = {} } } })
--> error: отправитель orders.send — функция или вызываемая таблица, а не nil
```

С отправителя спрашиваются только `send` и `features`: это чужой объект,
а не таблица настроек, и остальные его поля ящика не касаются.

### Запуск: `start`, `stop`, `flush`

```lua
outbox.start()   -- первый проход в этом файбере: спейсы заведены, такт пошёл
outbox.stop()    -- такт встал; строки остались на месте
outbox.flush()   -- один проход прямо сейчас, без такта
--> { sent = 0, dead = 0, more = false }
```

`start` зовут при подъёме узла, после `box.cfg` и до первой записи.
Первый проход идёт в файбере вызывающего, а не тактом: он заводит спейсы,
а заведение уступает, и запись, пришедшая в это окно, увидела бы ящик
недостроенным. Дальше вывоз идёт тактом `tnt-loop` раз в `interval`.
На узле для чтения заводить нечего: ящик приедет репликацией, а вывоз
там молчит.

Первый такт идёт сразу за `start`, и `flush`, позванный в тот же миг,
отвечает `skipped = 'проход уже идёт'`: проход такта ещё не кончился.

### Спейсы

| Спейс | Что лежит |
|---|---|
| `outbox` | `key` (последовательность), `id`, `name`, `message` — тело и настройки, `created` — стенное время записи или возврата |
| `outbox_dead` | `id`, `reason`, `buried` — когда зарыта, `row` — строка ящика целиком |
| `outbox_barrier` | одна строка: когда открыли нынешнее поколение |

Спейсы заводит **вывоз**, а не запись. Заведение — DDL, и оно уступает:
внутри чужой транзакции уступка порвала бы её, а рядом с записью
соседнего файбера показала бы ему спейс без индекса. Поэтому строит ящик
один — первый проход вывоза, — и спейс считается заведённым только
вместе с первичным индексом. Запись в незаведённый ящик — исключение:

```lua
outbox.write('order.paid', { order = 11 })   -- до outbox.start()
--> error: ящик ещё не заведён: позовите outbox.start() при подъёме узла
```

**Ключ строки — последовательность спейса.** Она не начинается заново
ни после удаления всех строк, ни после `truncate`, ни после перезапуска.
На ключе стоит граница поколения (раздел «Только зафиксированное»):
номер, начатый заново на опустевшем ящике, лёг бы под старую границу,
и строку незафиксированной транзакции вывоз счёл бы зафиксированной.
Ключ держит и порядок вывоза; опознаватель сообщения лежит в самой
строке.

### Запись: `write`

`outbox.write(name, body, opts) → id`. Опознаватель — ULID, и его же
несёт отправка: повтор вывоза после обрыва узнаётся получателем по нему.

```lua
local id = box.atomic(function()
    orders:replace({ 11, 'оплачен' })

    return outbox.write('order.paid', { order = 11 }, {
        headers = { ['x-tenant'] = 'acme' },
        timeout = 3,                             -- срок вызова отправителя на вывозе
    })
end)
```

| Ключ | Что |
|---|---|
| `headers` | свои заголовки поверх перенесённых контекстом; имена строчные, значения — строки |
| `key` | ключ порядка у отправителя; непустая строка |
| `delay` | не выдавать раньше срока, секунды, от 0 до ста лет |
| `ttl` | срок жизни сообщения, секунды, больше нуля и меньше ста лет |
| `priority` | порядок выдачи готовых: 0 — первым; целое не меньше нуля |
| `id` | готовый опознаватель вместо своего ULID; непустая строка |
| `timeout` | срок вызова отправителя на вывозе, секунды, больше нуля |

Настройки ложатся в строку и уходят с ней: их читает отправитель,
а не ящик. Настройку, которой отправитель не умеет по своим `features`,
запись отвергает исключением; незнакомый ключ — тоже исключение,
с перечнем знакомых:

```lua
outbox.write('order.paid', { order = 11 }, { key = 'o-11' })
--> error: настройки записи: «key» — отправитель не умеет

outbox.write('order.refunded', { order = 11 })
--> error: ящику некому отправлять «order.refunded»: отправитель не назван
```

**Отказа парой у записи нет.** Отказ box — узел для чтения, уступка
в транзакции — это отказ транзакции вызывающего, и он приходит к нему
так же, как отказ его собственной вставки. Исключение — и ошибка
программиста: незнакомая настройка, имя без отправителя, тело не из
простых данных, незаведённый ящик.

**Вне транзакции** запись идёт своей транзакцией на одну строку: так ящик
служит и надёжной отправкой без данных, которая переживает перезапуск.

**Тело — простые данные**: `nil`, логика, конечное число, строка
и таблицы из них с ключами-строками и ключами-числами. Тело едет в спейс
через msgpack, а оттуда к получателю обычно через JSON, где cdata
(`int64`, `decimal`, `uuid`, `datetime`) теряет род, а функция не ложится
вовсе. Большое целое едет строкой.

```lua
outbox.write('order.paid', { sum = require('decimal').new('1.5') })
--> error: тело.sum — простые данные, а не cdata
```

Пределы тела те же, что у всех очередей договора, — ящик проверяет тело
правилом того отправителя, которому его отдаст: **не глубже 100 таблиц**
и **не больше 10 000 значений**, считая каждую ссылку на таблицу так,
как её запишет кодек, и без колец. Тело, которое ящик принял, отправитель
на вывозе не отвергнет; негодное отвергается при записи, а не через час
неповторяемым отказом вывоза:

```lua
local ring = {}

ring.self = ring
outbox.write('order.paid', ring)
--> error: тело.self — кольцо: таблица лежит сама в себе
```

### Вывоз

Проход берёт начало ящика куском `batch`, отправляет строки по порядку
ключей и удаляет отправленные. Отчёт прохода говорит, чем он кончился:

| Поле | Что |
|---|---|
| `sent` | сколько строк ушло |
| `dead` | сколько зарыто |
| `more` | кусок вывезен целиком — в ящике осталось ещё |
| `skipped` | проход не шёл: `'узел только для чтения'`, `'отступ после отказа'` либо `'проход уже идёт'` |
| `err` | повторяемый отказ отправителя, на котором проход кончился |
| `stalled` | ключ строки, о фиксации которой ящик ещё не знает |

Кусок, вывезенный целиком, будит следующий проход сразу, не дожидаясь
такта: иначе миллион строк уезжал бы куском в секунду.

**Будильник вывоза — отметка фиксации**: событие уходит сразу
за транзакцией, а не в конце такта. Сам такт нужен ради строк, о которых
отметки нет: лежавших до запуска узла и вставленных мимо `outbox.write`.

Два прохода разом не идут: `flush`, позванный руками посреди такта,
возвращает `skipped = 'проход уже идёт'`. Иначе строку, которую такт уже
отправил и ещё не удалил, второй проход отправил бы второй раз.

Выборка идёт каждый раз с начала ящика, а не «после последнего
отправленного ключа»: под MVCC транзакция, взявшая ключ раньше,
фиксируется позже соседа с большим ключом, и курсор по ключу прошёл бы
мимо неё навсегда.

### Только зафиксированное

Без MVCC строку транзакции, ждущей записи в WAL или кворума синхронной
репликации, **видят все**, и `txn_isolation = 'read-confirmed'` без MVCC
этого не меняет. Вывоз, судящий по видимости, отправил бы событие,
которого после отката не было, — и взять его назад было бы нечем.
Поэтому вывоз берёт строку, только если знает о её фиксации:

- **отметка** — `box.on_commit` транзакции записи. Триггер приходит после
  записи в WAL и после кворума и не приходит при откате. Внутри него
  только отметка и толчок вывозу: уступка в `on_commit` роняет процесс.
  Триггер один на транзакцию, а не на строку;
- **граница поколения** — старший ключ, прочитанный перед записью
  барьера в `outbox_barrier`. Фиксация барьера ждёт всех, кто встал
  в WAL раньше: строки не старше границы, пережившие барьер,
  зафиксированы. Так вывозится лежавшее до запуска — отметок в памяти
  после перезапуска нет.

Строка, о фиксации которой ящик не знает, **останавливает проход**:
порядок ключей важнее скорости. Строка без отметки выше границы — это
вставка мимо `outbox.write`; вывоз стоит на ней не дольше пяти секунд
и открывает поколение заново, о чём пишет `warn`:

```lua
-- строка мимо outbox.write: отметки фиксации у неё нет
local key = box.space.outbox:insert({
    box.NULL, 'manual-1', 'order.paid',
    { body = { order = 12 }, options = { id = 'manual-1', headers = {} } },
    clock.realtime(),
}).key

outbox.flush().stalled   --> key: о фиксации не известно, проход стоит
-- пять секунд спустя
outbox.flush().sent      --> 1, в журнале «строка ящика легла мимо outbox.write»
```

### Отказы вывоза и зарытые: `dead`, `kick`

| Ответ отправителя | Что делает вывоз |
|---|---|
| `nil, err` с `err.retriable ~= false`, бросок, `nil, nil` | строка на месте, проход кончается, следующий — после отступа |
| `nil, err` с `err.retriable == false` | строка уходит в `outbox_dead` одной транзакцией с удалением, вывоз идёт дальше |
| имя, которому не назначен отправитель | как повторяемый отказ: строку ждёт настройка, а не человек |

Повторяемый отказ держит голову ящика: одна недоступная сторона
останавливает все события, зато порядок не рвётся. Видно это
по возрасту головы — `oldest_seconds` сводки и ряду
`outbox_oldest_seconds`; это главный ряд тревоги.
Отступ растёт с каждым отказом подряд и сбрасывается первым проходом,
дошедшим до конца куска. Неповторяемый отказ уводит строку в зарытые,
иначе одна негодная строка остановила бы все события навсегда.

`outbox.dead(limit)` отдаёт до `limit` зарытых по порядку опознавателя —
у ULID это порядок записи; без аргумента — сто:

```lua
outbox.dead()
--> { {
-->     id = '01M…', reason = 'вебхук order.paid ответил 422', buried = 1790…,
-->     row = { 7, '01M…', 'order.paid', { body = …, options = … }, 1790… },
--> } }

outbox.dead(0)
--> error: сколько взять — число больше 0, а не 0
```

`outbox.kick(count) → moved` возвращает зарытые на отправку, когда
отправителя починили, и отдаёт число возвращённых; без аргумента —
одну:

```lua
outbox.kick(1)         --> 1: строка снова в ящике, в хвосте
outbox.flush().sent    --> 1: ушла с тем же опознавателем
outbox.kick()          --> 0: зарытых больше нет
```

Возврат берёт те же строки, что показал бы `dead(count)`, и одной
транзакцией перекладывает их из `outbox_dead` в хвост ящика. Ключ
у строки новый — от последовательности, — а опознаватель, назначение,
тело и настройки отправки те же, что сохранила запись, вместе
с заголовками контекста. `created` — миг возврата: возраст головы
говорит, сколько строка ждёт вывоза, а когда она родилась — старшие
биты ULID.

**Порядок при возврате меняется**: возвращённая встаёт за строками,
записанными после её зарытия, и уходит после них. Старый ключ ей
не вернуть — он лежит под границей поколения, и вывоз счёл бы строку
зафиксированной раньше, чем зафиксировался возврат.

Отметку фиксации возврат ставит так же, как запись: возвращённая уходит
ближайшим проходом, а не через пять секунд по границе поколения, и такт
будит её отметка. Строку, вставленную в `outbox` руками, вывоз ждал бы
эти пять секунд и писал бы о ней `warn`.

Без аргумента возвращается одна строка: возврат — решение о той,
которую разобрали, и без числа оно не касается остальных. **Больше
тысячи за вызов — исключение**: возврат — одна транзакция без уступки,
и пока она идёт, узел не отвечает никому. Замер на Tarantool 3.8: тысяча
строк — 0,03 с, десять тысяч — 0,17 с, пятьдесят — около секунды,
а двести тысяч упираются в срез файбера и откатываются целиком. Больше
тысячи возвращают несколькими вызовами.

```lua
outbox.kick(1001)
--> error: сколько вернуть — число от 1 до 1000, а не 1001

box.atomic(function()
    outbox.kick(1)
end)
--> error: возврат зарытых идёт своей транзакцией, и в чужой его не зовут
```

В чужой транзакции возврат стал бы её частью: её откат молча вернул бы
строки в зарытые, а число возвращённых вызывающий уже получил бы.
Пары у возврата нет, как и у записи: возврат — тоже запись, и на узле
для чтения он отказывает исключением box, а зарытые остаются на месте.
Возвращённая строка, снова получившая неповторяемый отказ, зарывается
заново — с новой причиной и временем.

### Узел для чтения и смена ведущего

Ящик реплицируется вместе с данными. Прежний ведущий, став репликой,
перестаёт вывозить на первом же такте; новый открывает поколение
(барьер) и вывозит с начала. Строка, отправленная прежним, но не
удалённая до смены, уйдёт второй раз с тем же опознавателем — это и есть
«хотя бы раз», и повтор отсекает получатель по опознавателю.

```lua
box.cfg({ read_only = true })

outbox.flush().skipped
--> 'узел только для чтения'

outbox.write('order.paid', { order = 13 })
--> error: Can't modify data on a read-only instance - box.cfg.read_only is true
```

Запись на реплике отказывает так же, как всякая запись, — исключением box.

### Контекст и трасса

Опознаватель запроса и трасса едут в `headers` строки: запись кладёт туда
`context.export()` в миг вызова, поверх — заголовки вызывающего, они
главнее. Вывоз отдаёт отправителю сохранённые заголовки, а не заголовки
своего такта: трасса идёт от того, кто писал в ящик.

```lua
local context = require('tnt.context')

context.run({ request_id = 'r-7' }, function()
    outbox.write('order.paid', { order = 14 })
end)
-- на вывозе: opts.headers['x-request-id'] == 'r-7'
```

Своих крюков трассы у ящика нет: отрезок отправки заводит сам
отправитель, если умеет.

### Состояние и счётчики: `status`, `reset`

```lua
outbox.status()
--> {
-->     running = true, interval = 1, batch = 100,
-->     senders = { 'order.paid', 'order.shipped' },
-->     counts = { written = 12, kicked = 0, sent = 11, dead = 1, failures = 0, stale = 0 },
-->     pending = 0, dead = 1, oldest_seconds = nil,
-->     boundary = 0, generation = 1790182560.5, holding = false,
--> }
```

| Поле | Что |
|---|---|
| `running` | идёт ли такт вывоза |
| `interval`, `batch` | действующие настройки |
| `senders` | имена назначений по алфавиту |
| `counts.written` | записано строк |
| `counts.kicked` | возвращено из зарытых |
| `counts.sent` | отправлено и удалено |
| `counts.dead` | уведено в зарытые |
| `counts.failures` | повторяемых отказов, после которых вывоз отступал |
| `counts.stale` | строк, вывезенных по границе поколения вместо отметки |
| `pending` | сколько строк ждёт вывоза |
| `dead` | сколько строк в `outbox_dead` |
| `oldest_seconds` | возраст головы ящика по стенным часам; пустота — ящик пуст |
| `boundary` | граница нынешнего поколения; у поколения, открытого на пустом ящике, — 0 |
| `generation` | когда поколение открыли; пустота — не открывали, и первый же проход откроет |
| `holding` | вывоз стоит в отступе после отказа |

До заведения ящика сводка не падает: `pending` и `dead` — нули.

`outbox.reset()` останавливает вывоз и забывает настройки, счёт,
отступ и отметки. Строки в спейсах остаются: их стирает тот, кто заводил
узел.

### Ряды метрик

Сводка видна и рядами в реестре встроенного `metrics` (`tnt-metrics`):

| Ряд | Род | Метки | Что значит |
|---|---|---|---|
| `outbox_depth` | gauge со сбором | `state`: `pending`, `dead` | сколько строк ждёт вывоза и сколько лежит в `outbox_dead` — `pending` и `dead` сводки |
| `outbox_oldest_seconds` | gauge со сбором | — | сколько секунд ждёт голова ящика — `oldest_seconds` сводки; у пустого ящика ноль |
| `outbox_sent_total` | counter | `destination` | отправлено и удалено; растёт с `counts.sent` |
| `outbox_dead_total` | counter | `destination` | зарыто неповторяемым отказом; растёт с `counts.dead` |

```lua
outbox.configure({ senders = { ['order.paid'] = webhook } })
outbox.start()
outbox.write('order.paid', { order = 11 })
outbox.flush()
outbox.write('order.paid', { order = 12 })   -- лежит до следующего прохода
```

```
outbox_depth{state="pending"} 1
outbox_depth{state="dead"} 0
outbox_oldest_seconds 0.010433673858643
outbox_sent_total{destination="order.paid"} 1
```

**Возраст головы — главный ряд тревоги.** Повторяемый отказ держит
голову, и все события за ней стоят: вывоз, стоящий на отказе брокера,
иначе не виден. Правило тревоги — `outbox_oldest_seconds > 300`.
У пустого ящика голова ждёт ноль секунд, а не пропадает из выкладки:
правило на пропавшем ряде молчит, и пустой ящик не должен выглядеть
узлом, который перестали собирать. Отрицательный возраст — часы
прежнего ведущего впереди — идёт нулём; сводка показывает часы как есть.

**Ряды свои, `outbox_*`, а не ряды сообщений `message_*`.** Из ящика
отправляет отправитель — очередь или клиент брокера, — и он сам считает
отправленное в `message_*` под тем же именем назначения: ящик, считающий
туда же, сложил бы каждое событие дважды. Своё у ящика — то, чего
отправитель не видит: строки, которые ещё не ушли.

Шкалы собираются перед каждой выкладкой — это длина спейса и первая
строка индекса, — и на узле, где ящик не заведён, их строк нет вовсе.
Реплика показывает то же, что ведущий: ящик реплицируется вместе
с данными, и голова, которую никто не вывозит, стареет и там. Сумма
по кластеру поэтому считает ящик столько раз, сколько у него копий;
глубину репликасета берут наибольшим числом по его узлам. Потолок
назначений в счётчиках — сто (`require('tnt.outbox.series').DESTINATIONS`),
сверх него назначение идёт словом `_other`.

### Журнал

Тело события в журнал не пишется: в нём бывают персональные данные.
Пишутся имя назначения, опознаватель, ключ строки и причина.

| Событие | Уровень |
|---|---|
| строка ящика зарыта | `error` |
| вывоз отложен после отказа, строка легла мимо `outbox.write`, такт вывоза или уборки отметок не отработал | `warn` |
| вывоз ждёт голову ящика | `debug` |

Отложенный вывоз пишется с подавлением повторов: брокер, лежащий час,
иначе писал бы строку на каждый такт.

### Отметки получателя: `tnt.outbox.inbox`

Гарантия хотя бы раз — у всех долговечных очередей: у ящика, у очереди
в спейсе, у брокеров AMQP и Kafka. Сообщение, обработанное перед обрывом,
приходит снова с тем же `id`, и отсечь его может только получатель:
очередь не знает, успел ли обработчик записать своё. Модуль
`tnt.outbox.inbox` ставит отметку «получатель, `id`» в транзакции
обработчика:

```lua
local inbox = require('tnt.outbox.inbox')

inbox.start()                                        -- при подъёме узла: спейс заведён, уборка пошла

local function on_paid(message)
    box.atomic(function()
        if inbox.claim('receipts', message) then     -- false — повтор: делать нечего
            box.space.receipts:insert({ message.id, message.body.order })
        end
    end)
end
```

| Вызов | Что делает |
|---|---|
| `inbox.claim(receiver, message)` | ставит отметку в транзакции вызывающего: `true` — впервые, `false` — повтор |
| `inbox.configure(opts)` | срок хранения `retention`, такт `interval`, кусок `batch`; негодное — исключение |
| `inbox.start()` | первый проход уборки в файбере вызывающего — спейс заведён, — затем такт |
| `inbox.sweep()` | один проход уборки прямо сейчас; отчёт `{ removed, more, skipped }` |
| `inbox.stop()` | останавливает такт; отметки остаются |
| `inbox.status()` | такт, настройки, число отметок, возраст старшей, счётчики |
| `inbox.reset()` | останавливает такт, забывает настройки и счёт; отметки остаются |

#### Отметка: `claim`

**Отметка — вставка в транзакцию обработчика.** Фиксация оставляет
и запись, и отметку; откат снимает обе, и повтор после отката
обрабатывается заново, как и должен:

```lua
local message = { id = '01JA0000000000000000000007', body = { order = 7 } }

box.begin()
inbox.claim('receipts', message)                     --> true
box.space.receipts:insert({ message.id, message.body.order })
box.rollback()                                       -- ни записи, ни отметки

box.atomic(inbox.claim, 'receipts', message)         --> true: после отката — снова впервые
box.atomic(inbox.claim, 'receipts', message)         --> false: повтор
```

**Вне транзакции отметка — исключение.** Поставленная отдельно
от записи, она либо переживёт несделанную запись и проглотит повтор,
либо не успеет и ничего не отсечёт:

```lua
inbox.claim('receipts', message)
--> error: отметку ставят в транзакции обработчика: без его записи она повтор не отсекает
```

**Ключ — получатель и `id`.** Одно событие обрабатывают несколько
получателей, и отметка одного не вправе отсечь другого:

```lua
box.atomic(inbox.claim, 'mail', message)             --> true: у получателя mail свои отметки
```

Имя получателя — латинская буква, дальше буквы, цифры, подчёркивание,
точка и дефис: `receipts`, `billing.invoice-sent`. Из сообщения нужен
только `id` — непустая строка; конверт любой очереди договора его несёт.
Негодный аргумент — исключение на строке вызывающего:

```lua
box.atomic(inbox.claim, 'Чеки', message)
--> error: имя получателя — строка по образцу ^%a[%w_.-]*$, а не «Чеки»

box.atomic(inbox.claim, 'receipts', { id = '' })
--> error: сообщение.id — непустая строка, а не пустая
```

**Две доставки разом отсекает box.** Без MVCC уступки внутри транзакции
нет, и вторая видит отметку первой уже в миг вставки, до записи в WAL;
откатится первая — её доставка откажет и придёт снова, как после всякого
отказа обработчика. Под MVCC вторая может отметки первой не увидеть,
но тогда её откатывает конфликт фиксации: из двух обработчиков,
уступивших между отметкой и записью, фиксируется один, второй получает
«Transaction has been aborted by conflict» (проверено на 3.8).

Счётчики `claimed` и `repeated` растут в миг вызова, а не фиксации:
отметка, откаченная вместе с транзакцией, в них уже учтена.

#### Спейс

| Спейс | Что лежит |
|---|---|
| `outbox_inbox` | `receiver`, `id` — ключ; `marked` — стенное время отметки, по нему судит уборка |

Первичный индекс — по получателю и `id`, второй, `marked`, неуникальный —
по времени отметки. Имя начинается с имени пакета, как у спейсов ящика:
спейс `inbox` у приложения бывает своим.

Спейс заводит **`start`**, а не отметка: заведение — DDL, оно уступает
и в транзакции обработчика порвало бы её. Спейс считается заведённым
только вместе с индексом времени, а до того отметка — исключение:

```lua
box.atomic(inbox.claim, 'receipts', message)        -- до inbox.start()
--> error: отметки получателя ещё не заведены: позовите inbox.start() при подъёме узла
```

Спейс — memtx. Обработчик, который пишет в vinyl, отмечает в той же
транзакции только при `memtx_use_mvcc_engine = true`: без MVCC ядро
не смешивает движки в одной транзакции и отказывает «MVCC is unavailable
for storage engine 'memtx' so it cannot be used in the same transaction
with 'vinyl', which supports MVCC» (3.8).

#### Уборка по сроку

```lua
inbox.configure({ retention = 3 * 86400, interval = 60, batch = 1000 })
```

| Ключ | Что | Умолчание |
|---|---|---|
| `retention` | сколько хранить отметку, секунды; больше нуля | 604 800 — неделя |
| `interval` | как часто идёт уборка, секунды; больше нуля | 60 |
| `batch` | сколько отметок стирается одной транзакцией; целое больше нуля | 1000 |

Настройки задаются разом: не названное теперь возвращается к умолчанию,
и `box.NULL` значит то же, что нет ключа. Негодное — исключение
на строке вызывающего:

```lua
inbox.configure({ retention = 0 })
--> error: настройки отметок.retention — число больше 0, а не 0
```

**Срок — не меньше самого длинного окна повтора** у очередей, из которых
получатель берёт сообщения: повтор, пришедший после уборки своей
отметки, обработается второй раз. Умолчание — неделя: столько
по умолчанию Kafka хранит тему и смещения группы, и группа, простоявшая
до недели, перечитывает от своего смещения то, что успела обработать
и не успела подтвердить. Это самое длинное окно из тех, что стоят без
настройки; очередь в спейсе, ящик и брокер AMQP повторяют обычно через
минуты — после срока взятия, обрыва или перезапуска.

Цена недели — память. Отметка получателя из восьми букв с ULID занимает
около 110 байт арены вместе с обоими индексами (замер на 3.8): неделя
по десять сообщений в секунду — шесть миллионов отметок и около 660 МБ,
по сто в секунду — 6,6 ГБ. Получателю с большим потоком и коротким
окном повтора срок сокращают.

Проход уборки идёт **только на узле для записи**: уступка, затем выборка
до `batch` отметок старше срока по индексу `marked` и их стирание одной
транзакцией. Кусок, стёртый целиком, будит следующий проход сразу,
не дожидаясь такта. Курсора нет: стёртое не возвращается, и каждый кусок —
снова то, что старше срока; отметка, поставленная за уступкой, моложе
срока и в кусок не попадает. Уборка внутри транзакции — исключение:
она уступает, а уступка порвала бы транзакцию вызывающего.

| Поле отчёта | Что |
|---|---|
| `removed` | сколько отметок стёрто |
| `more` | кусок стёрт целиком — старое, может быть, ещё осталось |
| `skipped` | проход не шёл: `'узел только для чтения'` |

```lua
inbox.sweep()
--> { removed = 0, more = false }

box.cfg({ read_only = true })
inbox.sweep()
--> { removed = 0, more = false, skipped = 'узел только для чтения' }
```

На реплике уборка молчит: стирание приедет от ведущего. Ожидания после
смены ведущего нет — уборка стирает только старое, и стирание, пришедшее
хвостом прежнего ведущего, стирает то же самое.

#### Сводка: `status`

```lua
inbox.status()
--> {
-->     running = true, retention = 604800, interval = 60, batch = 1000,
-->     marks = 2, oldest_seconds = 30,
-->     counts = { claimed = 2, repeated = 1, removed = 0 },
--> }
```

| Поле | Что |
|---|---|
| `running` | идёт ли такт уборки |
| `retention`, `interval`, `batch` | действующие настройки |
| `marks` | сколько отметок в спейсе |
| `oldest_seconds` | возраст старшей отметки по стенным часам; пустота — отметок нет |
| `counts.claimed` | отметок поставлено — в миг вызова |
| `counts.repeated` | повторов отсечено — в миг вызова |
| `counts.removed` | отметок стёрто уборкой |

Главный ряд тревоги — `oldest_seconds`: уборка, которая не идёт, видна
по нему раньше, чем по памяти, — возраст старшей уходит за срок хранения.
До заведения спейса сводка не падает: `marks` — ноль, `oldest_seconds` —
пустота.

### Подмена в проверках

Внешние зависимости объявлены через `tnt-external` и подменяются
`_set_source` по одному имени; остальные остаются настоящими.

| Модуль | Имена |
|---|---|
| `tnt.outbox.shipper` | `space` (модуль спейсов: `open`, `head`, `first`, `top`, `barrier`, `remove`, `bury`, `depth`), `now` — время планировщика, `realtime` — стенное время, `read_only` — пишет ли узел |
| `tnt.outbox.commit` | `in_txn`, `txn_id`, `on_commit`, `on_rollback` — транзакция вызывающего и её исход |
| `tnt.outbox.inbox` | `in_txn` — есть ли транзакция вызывающего, `read_only` — пишет ли узел, `realtime` — стенное время отметки и срока |

```lua
local shipper = require('tnt.outbox.shipper')

shipper._set_source({ read_only = function() return true end })
outbox.flush().skipped      --> 'узел только для чтения'
shipper._set_source(nil)    -- настоящие средства вернулись
```

Так проход вывоза проверяется на двойнике спейсов без узла, а отметки
фиксации — на двойнике транзакции. Отметкам получателя подменяют стенные
часы: отметка «старше срока» ставится на заданный миг, а не ждётся неделю.

## Чем пришлось поступиться

- **Голова ящика ждёт отправителя.** Строгий порядок ключей значит, что
  одна недоступная сторона держит все события, в том числе других
  назначений; видно это только по возрасту головы — `oldest_seconds`
  сводки и ряду `outbox_oldest_seconds`.
- **Хотя бы раз, а не ровно один.** Обрыв между отправкой и удалением
  строки и смена ведущего дают повтор с тем же опознавателем. Отсекает
  его получатель — отметкой `tnt.outbox.inbox` в той же транзакции, что
  и его запись, либо ключом идемпотентности на своей стороне.
- **Повтор после уборки своей отметки проходит.** Отметки живут срок
  хранения, и повтор, пришедший позже, обработается второй раз. Срок
  ставят не меньше самого длинного окна повтора; неделя по умолчанию
  стоит памяти — около 110 байт на отметку.
- **Отметки — в памяти узла, в memtx.** Обработчик, пишущий в vinyl,
  отмечает в той же транзакции только под MVCC: без него ядро не смешивает
  движки в одной транзакции.
- **Время отправки у получателя — миг вывоза, а не записи.** Конверт
  сообщения собирает отправитель, и отдать ему готовый конверт вызовом
  `send` нечем: `id`, `headers` и `key` едут настройками, а поля времени
  рождения среди них нет. Когда сообщение родилось, говорят старшие биты
  его ULID; сколько оно пролежало в ящике — `oldest_seconds`.
- **Имя без отправителя стоит вечно.** Такая строка не уходит
  и не зарывается: её ждёт настройка. Лечится `configure` с нужным
  именем; пока его нет, растут `pending` и возраст головы.
- **Возвращённое встаёт в хвост.** `kick` кладёт строку с новым ключом:
  старый лежит под границей поколения. Строки, записанные после её
  зарытия, уходят раньше неё. Зарытое хранится по опознавателю,
  и вторая зарытая строка с тем же готовым `id` заменяет первую.
- **Возврат — не больше тысячи строк за вызов.** Он идёт одной
  транзакцией без уступки и держит узел; тысяча строк — сотые доли
  секунды, а остальное возвращают следующими вызовами.
- **Спейсы заводит сам пакет, а не миграция `tnt-schema`.** Ящик
  появляется на узле первым проходом вывоза, и до `outbox.start()` запись
  в него — исключение с прямым указанием его позвать. Цена — узел,
  на котором ящик только пишут, а вывозят откуда-то ещё, всё равно зовёт
  `start` или хотя бы `flush`.
- **Тело — не больше десяти тысяч значений и ста таблиц вглубь.**
  Предел общий для очередей договора, и выгрузка, положенная
  в сообщение, отвергается при записи. Одна таблица, положенная во много
  веток, считается столько раз, сколько её напишет кодек: в памяти такое
  тело маленькое, а в строке и у брокера — нет.
- **Проход идёт в одном файбере.** Отправка строк — по одной, по порядку:
  параллельная отправка сломала бы порядок ключей, ради которого ящик
  и читает спейс с начала. Вывоз ждёт ответа на каждую строку, прежде
  чем взять следующую.
- **Глубина ящика — без назначения.** Длину спейса box отдаёт сразу,
  а разбивка по назначению — это обход всего ящика на каждом сборе;
  поэтому по назначению идут только счётчики вывоза.
- **Отметок получателя в рядах нет.** Их число и возраст старшей отдаёт
  `inbox.status()`; в ряды их переводит приложение.

## Проверки

Проверки лежат в `test/` и идут на luatest: `.rocks/bin/luatest test/`.
Модули пакета берутся из исходников, зависимости — установленными.

В процессе проверок — то, что решает сам пакет: настройки и их тексты
отказа, признаки отправителя у записи и пределы тела на строке
вызывающего (сами проверки настроек и тела — у `tnt-message`), строка,
собранная записью,
отметки фиксации на двойнике транзакции, проход вывоза на двойнике
спейсов — порядок, итоги отправителя, отступ, граница поколения,
строка мимо записи, отчёт и сводка, такт и его сорвавшийся проход;
ряды — ушедшее и зарытое по назначению, глубина и возраст головы,
пустой ящик, голова из будущего и незаведённый ящик без шкал;
аргументы возврата зарытых и возврат в чужой транзакции;
у отметок получателя — умолчания, настройки, аргументы отметки, отметка
вне транзакции и до заведения спейса, уборка в транзакции и на узле
без записи, такт уборки и его сорвавшийся проход.
Отказы аргументов сверяются текстом и местом: винится строка вызывающего.

Три группы поднимают узел Tarantool через luatest. Первая — настоящие
спейсы ящика: запись в транзакции и вне её, откат, ключ последовательности
после опустевшего ящика, повторяемый и неповторяемый отказ, барьер
поколения после перезапуска, узел для чтения, будильник отметки,
кольцо в теле — до вставки строки, недостроенный спейс и сводка;
возврат зарытых — тот же опознаватель и те же настройки в хвосте ящика
и отправка ближайшим проходом, порядок показа `dead`, чужая транзакция
и реплика, недостроенный спейс зарытых; ряды на настоящих спейсах —
глубина, возраст головы и счётчики после прохода. Вторая — синхронная
транзакция, которая ждёт кворума и откатывается по сроку: её строку видит
простое чтение, а вывоз её не отправляет. Третья — отметки получателя:
две доставки одного `id` дают одну запись обработчика, откат его
транзакции снимает отметку, уборка стирает отметки старше срока и не
трогает отметку ровно на горизонте, кусок стирается одной транзакцией,
реплика не стирает ничего, `start` заводит спейс, полный кусок будит
следующий проход, недостроенный спейс отметку не принимает.

Покрытие строк — 100 %, убитых мутантов — 100 % (87 проверок, 26 из них —
на узлах).
